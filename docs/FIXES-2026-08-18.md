## 🟠 عالية (أمن وخصوصية)

- `getTenantSettings` كان يسرّب `backupSheetSecret` لأي دور → select محدد + حذف المفاتيح الحساسة.
- `getJustDueFollowUps`/`getOverdueFollowUpsCount` بلا `assertRole` → PROVIDER كان يحصد أسماء/أرقام كل العملاء كل 30ث عبر due-watcher → `ROLE.OWNER_ADMIN_COORDINATOR` + إخفاء هادئ في الواجهة.
- توسيع تقييد المنسق (عملاؤه/حملاته) ليشمل: `createBooking`, `quickCreateBooking`, `updateLead`, `changeLeadStage`, `getLeadById`, `createFollowUp`, `searchLeadByPhone`, `archiveLead`, `unarchiveLead` عبر حارس مشترك `assertCoordinatorCanAccessLead`.
- `getBookingsSummary` كان يعرض للمنسق حجوزات كل المنشأة → تقييد بنفس فلتر `getBookings`.
- أخطاء النظام (`tenantId = NULL`) كانت تظهر لكل الشركات في /settings/errors → إسقاط فرع `isNull`.
- CSV formula injection في التصدير → تحييد الخلايا البادئة بـ `= + - @`.
- ترقيات أمنية: `next` 16.2.3→**16.3.1** (23 advisory بينها proxy bypass)، `better-auth` →**1.7.0** (critical: stale sessions بعد حذف المستخدم وغيرها)، `xlsx` 0.18.5→**0.20.3** (Prototype Pollution + ReDoS — النسخة المُصحّحة غير منشورة على npm فأُدرجت كـ vendored tarball في `vendor/`)، + `npm audit fix` (postcss/sharp/nanoid/kysely/js-yaml/brace-expansion).
- رؤوس أمان على **كل** المسارات عبر `next.config.ts` (X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, HSTS) + `poweredByHeader: false`؛ استثناء `sw.js` من proxy matcher (مفتاح القتل كان غير قابل للوصول).
- `assertEnv()` كان كوداً ميتاً → `instrumentation.ts` يستدعيه عند الإقلاع في الإنتاج؛ RESEND_API_KEY بدون EMAIL_FROM = خطأ إقلاع؛ `sslmode=require` خُفّض لتحذير؛ `sanitize()` لا يكسر كلمات المرور المحتوية على مسافات.
- webhook: dedup داخل الدفعة + فحص المكررات **بعد** قفل FOR UPDATE + مقارنة timing-safe للسر القديم مع ترقية فعلية للـ hash عند المطابقة.
- `log-client-error` بلا حدود → zod + rate limit 10/دقيقة.
- `testMyWhatsappCredentialsAction` (إرسال مدفوع حقيقي) → rate limit 5/ساعة.
- `updateDepartment` بلا تحقق → نقل تحققات addDepartment (فجوة سالبة كانت تعطّل حجوزات القسم بخطأ tstzrange خام).
- `getWebhookKeys` كان يرسل `secretHash` للعميل → select صريح يستثنيه.
- فتح حساب يتيم: RESEND مفعّل + cleanup cron بحذف بعد ساعة (TTL التفعيل) → النافذة 72 ساعة + فحص env.

## 🟡 منطق المنتج والترابط

- **مرحلة "حجز" (isBooking) كانت ميتة** لكل مستأجر جديد → تزرع في `createTenantForUser` + هجرة backfill `0015` للمستأجرين الحاليين.
- **عميل مؤرشف يعود عبر webhook** كان يُسقط بصمت كمكرر → إعادة تفعيل تلقائية (DNC يبقى محظوراً) + تسجيل نشاط.
- **لا إشعار NEW_LEAD** عند إسناد round-robin → إشعار للمنسق المُسنَد داخل معاملة الـ webhook.
- تعريف "التحويل" موحّد على `bookingStatus = COMPLETED` في /analytics (كان بأسماء مراحل قابلة للكسر عند إعادة التسمية) + استثناء المؤرشفين + حدود الرياض للشهر والمخطط اليومي.
- قمع التحليلات: "تم التواصل" تتطلب `completedAt`، و"ردّوا" أصبحت type-based.
- زر "تواصلت" في المُهمَلين كان ينشئ متابعة **معلّقة** تُطلق تنبيهاً زائفاً → أكشن `markLeadContacted` الجديد.
- خانة "الحجز رغم التعارض" (مستحيلة النجاح بسبب قيد EXCLUDE) → حُذفت.
- روابط `/leads?search=` الميتة → تُقرأ server-side وتُمرر للواجهة؛ حد العرض 200 مع ملاحظة صادقة.
- صفحة العملاء: أزرار الاستيراد/الجماعية/التصدير تُخفى عن المنسق (كانت تفشل في آخر خطوة)؛ /team تردّ المنسق؛ login يحترم `?next=`.
- عدّادات "الترحيب العالق" كانت تحسب عملاء بلا ترحيب مقرر أصلاً → مقصورة على webhook sendWelcome + غير مؤرشفين.
- سجل النشاطات: إكمال/إلغاء المتابعة كانا يُسجَّلان "أضاف متابعة" → قيم enum جديدة `FOLLOW_UP_COMPLETED/CANCELLED` (هجرة `0016`) + ترجمات عربية + `WHATSAPP_FAILED`.
- نصوص واتساب المتناقضة بعد سياسة "لا fallback" → صياغة موحّدة صادقة في 3 واجهات.
- إصلاح ~15 معالجاً بلا try/catch (كانت تضرب error boundary الصفحة كاملة) + تراجع تفاؤلي عند الفشل.
- إصلاحات RTL (توسيط التوست `translate-x-1/2`)، توقيت الرياض في الواجهة (تذكير سريع/شارات/حدود min)، hydration عبر `useNow`.

## حادثة نشر 2026-08-18/19 (postmortem موجز)

**التسلسل:** دُفعت الجولة → فشل بناء `npm ci` (قفل npm 11 لا يجتاز تحقق npm 10 الصارم — أُصلح بإضافة esbuild صريحة + node 22) → النشر التالي ماتت حاويته أثناء فحص الصحة لأن المُهاجر الجديد (fail-fast) اصطدم بانحراف بيانات الإنتاج → الموقع 503.

**الجذر:** تكرارات `(tenant_id, name)` في `pipeline_stages` تراكمت بصمت لأن المُهاجر القديم ابتلع فشل 23505 لشهور — فشل الفهرس الفريد أسقط 0015 (42P10).

**ما تغيّر بنيوياً:**
- `start.sh` يتسامح مع فشل الهجرة (لا downtime) والمُهاجر يكتب ملف حالة في tmpdir.
- `/api/health?strict=1` يعرض `checks.migration` + تفاصيل الفشل — تشخيص الهجرات دون سجلات الحاوية (هكذا شُخّصت هذه الحادثة).
- هجرة `0001z_dedupe_pipeline_stage_names.sql` تنقل leads المكررات وتحذفها (مُتحققة بمحاكاة كاملة محلياً).
- فحص env عند الإقلاع يسجّل بصوت عالٍ ولا يُسقط الإقلاع أبداً.
- ENCRYPTION_KEY بأي صيغة يعمل (اشتقاق SHA-256 لغير الـ 64-hex) — كانت معطّلة في الإنتاج.

**درس:** أي هجرة جديدة يجب أن تُختبر على نسخة من بيانات الإنتاج الفعلية (أو محاكاة انحرافها) قبل الدفع — القاعدة النظيفة وحدها لا تكفي.
